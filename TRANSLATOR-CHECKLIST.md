# Переводчик и проверка Cloudflare Pages

## Текущие возможности переводчика

- Работает только на Cloudflare Pages (или другом хостинге, который запускает Pages Functions). GitHub Pages публикует только статические файлы и не исполняет `functions/api/translate.js`.
- На первом этапе поддержаны текст, вставка, `.txt`, `.md`, `.markdown`, `.log`, `.srt`, `.vtt` до 5 МБ и 200 000 символов. Каждый запрос к поставщику содержит до 1 000 символов; интерфейс показывает процент завершения и явную ошибку вместо вечных 10%.
- `.docx`, `.epub`, `.pdf`, сканы, изображения и другие структурированные форматы пока явно отклоняются. Не переименовывайте их в `.txt`: это не сохраняет разметку и может испортить файл. OCR ещё не подключён.
- Без `DEEPL_API_KEY` используется демонстрационный Google Translate endpoint без SLA. Для production задайте секрет DeepL API в Pages → Settings → Variables and Secrets. Ключ хранится только на сервере. Настройте квоту/оплату у провайдера и проверьте доступность выбранных языков.

## Быстрая проверка Cloudflare Pages

1. Подключите `Lina1209/Mirror-info-` к Cloudflare Pages. Выберите ветку, содержащую исправления. Build command оставьте пустой, output directory — `.`.
2. Дождитесь успешного production deploy. Убедитесь, что endpoint доступен: `GET https://<ваш-домен>/api/translate` должен вернуть JSON с `ok: true`.
3. Откройте сайт именно на домене Pages/вашем Cloudflare-домене. На `github.io` Functions не работают; переводчик должен показать понятную ошибку о недоступном API.
4. Добавьте `DEEPL_API_KEY` как **secret** в Pages → Settings → Variables and Secrets. Ключ не добавляйте в исходники или HTML. После добавления переменной выполните новый deploy.
5. Проверьте перевод короткого текста, затем TXT, MD, SRT или VTT. Проверьте прогресс до 100%, предпросмотр, скачивание, недоступную сеть и ошибку неверного ключа.

## D1 / заявки / Cloudflare Access

Эти настройки нужны для заявок и кабинета, но не являются зависимостью перевода текста:

1. Создайте D1 `mirror-info-orders`, примените `schema.sql` и настройте Pages D1 binding с именем `DB` на ту же базу.
2. Добавьте необходимые переменные/секреты: `IP_HASH_SALT`; для уведомлений — Telegram или Resend credentials. Не публикуйте секреты.
3. Для защищённого кабинета/админки создайте Cloudflare Access application и allow policy для конкретных email, желательно с MFA.
4. Настройте Pages variables `CF_ACCESS_TEAM` и `CF_ACCESS_AUD` согласно Access team domain и Audience Tag приложения. Защитите страницы/маршруты Access policies; сама статическая HTML-страница не скрывает содержимое, поэтому API также проверяет JWT.
5. Тест: отправить заявку, убедиться в записи D1; запрос `/api/admin/orders` без валидного Access JWT должен быть отклонён; после входа администратор может видеть и менять статусы. `/api/account` должен показывать только заявки с email вошедшего пользователя.
6. Если используются Preview deployments, отдельно задайте bindings и секреты для Preview environment и ограничьте к нему доступ.

## Следующие этапы форматов

Добавлять по очереди и отдельно тестировать на реальных образцах: (1) DOCX с обработкой run-ов и таблиц без потери стилей; (2) EPUB с переводом только XHTML-контента и неизменным контейнером/навигацией; (3) PDF с текстовым слоем и явным текстовым результатом; (4) OCR для сканов через отдельный провайдер и отдельную квоту. Не заявлять сохранение исходной PDF-вёрстки до реализации и проверки восстановления страниц.
